# ADR-003 — Domain-aware canonical skill resolution

**Status:** Proposed — technical/product-owner approval pending  
**Date:** 2026-11-15  
**Scope:** Build with AI skill registry, roadmap curriculum graph and skill-resource identity  
**Working branch:** `docs/build-with-ai-engineering-readiness`  
**Related:** [Build with AI target architecture](BUILD-WITH-AI-TARGET-ARCHITECTURE.md), [ADR-002](ADR-002-durable-roadmap-job-processing.md), [readiness issue #43](https://github.com/yashodipdeore2006/BuddyForStudy.V2/issues/43)

## 1. Decision to be made

Define a safe canonical identity and matching policy for skills generated by Gemini and reused across roadmaps.

The registry must reduce duplicate concepts without merging distinct skills, preserve stable identifiers already stored in courses and resource-prior records, and make the matching decision explainable.

This ADR proposes a conservative policy. It does not approve a production migration or runtime change.

## 2. Verified current implementation

Source files reviewed on `main` (baseline recorded in issue #43):

- `server/src/services/skillRegistry.service.js`
- `server/src/models/Skill.js`
- `server/src/services/domainPlaybooks.js`
- `server/src/services/aiRoadmap.service.js`
- `server/src/services/aiRoadmap.personalization.test.js`
- `server/test/skillResourcePrior.test.js`

### Current resolver behavior

1. `resolveCanonicalSkill` reads every skill document with `model.find({})`; it does not scope candidate lookup by domain.
2. It checks exact normalized name/alias, then slug/ID match, then token Jaccard similarity.
3. Fuzzy matching accepts the first highest-scoring candidate at a hardcoded score of 0.8. It does not require a distinct margin over the second-best candidate or report ambiguity.
4. A matched record automatically receives the generated input name and supplied aliases, including when the match was only fuzzy.
5. New canonical IDs are based only on the normalized name slug. The `Skill` collection has a globally unique string `_id`, so identical slugs cannot represent distinct concepts in separate domains.
6. `getRelevantCanonicalSkills(topic, 40)` also reads/ranks the entire registry without a domain parameter. `generateWithGemini` calls it without passing its available domain context.
7. `Skill` stores one scalar `domain` (default `general`) and has an index on `{ domain: 1, name: 1 }`, but the resolver does not use that scope.
8. Roadmap domain resolution already provides controlled values: `software_web`, `programming`, `data`, `exam`, `language`, `creative`, and `general`. `buildCourse` resolves the domain before calling the skill resolver.
9. Normalization uses ASCII-oriented character classes and tokenization drops tokens of length one. This can discard non-Latin skill text and single-letter language names such as C or R.
10. The repository tree contains `aiRoadmap.personalization.test.js` and resource-prior tests, but no dedicated `skillRegistry.service.test.js` file was found. The existing resource-prior test verifies aggregation by canonical ID; it does not prove resolver matching behavior.

### Consequences and failure cases

- A skill with the same spelling in two domains can be incorrectly reused.
- Similar phrases can be merged based on an arbitrary fixed score, even when the second-best candidate is nearly tied.
- A false fuzzy match can permanently pollute the canonical record's alias list and affect later roadmaps.
- Gemini may be shown relevant skills from unrelated domains in its prompt.
- Slug-only identity creates global collisions and cannot represent domain-specific homonyms cleanly.
- Unicode names and one-character skills may fail to normalize or participate in candidate matching.

## 3. Proposed canonical identity model

### 3.1 Treat a skill as a concept, not merely a text label

A canonical skill record should represent one meaning. Its display name and approved aliases are labels for that concept, not independent identities.

Proposed conceptual fields:

| Field | Purpose |
|---|---|
| `_id` | Stable canonical skill identifier; never regenerate during ordinary resolution |
| `name` | Preferred display name |
| `aliases` | Approved, normalized-equivalent names only |
| `domain` | Legacy/primary domain retained for compatibility |
| `domainScopes` | Explicit list of domains in which this concept is valid |
| `reviewStatus` | `approved` or `provisional` (or equivalent governance state) |
| `createdAt`, `updatedAt` | Registry lifecycle timestamps |
| alias provenance | Who/what supplied or approved an alias and when, without storing unnecessary learner PII |

Existing `domain` values must remain readable. Backfill `domainScopes` from the existing `domain` value before relying on the new field. Do not reinterpret `general` as a wildcard: cross-domain reuse must be explicit.

A genuinely shared concept may list multiple domains in `domainScopes`. A domain-specific concept should remain separate even when its label resembles a concept elsewhere.

### 3.2 Stable identifier policy

- Existing canonical IDs referenced by courses, roadmap lessons, resource priors or feedback must remain valid. Do not rename them as part of a resolver refactor.
- New IDs should be deterministic and domain-qualified so that the same slug in separate domains cannot collide. The exact encoding must be length-bounded, collision-checked and covered by tests.
- An ID collision must trigger a scoped lookup and explicit conflict handling; it must never silently return a record from a different domain.
- A canonical merge is a separate migration, not an alias update. It requires an explicit source-ID → target-ID mapping and an audit of every dependent reference (course lesson, resource prior, feedback, caches and analytics).

## 4. Proposed resolution algorithm

The resolver should return a structured decision rather than only an ID/name tuple:

`{ id, name, domainScopes, matchType, confidence, candidates, reviewRequired }`

The exact public shape can be internal initially; it should be typed and tested.

### Step 1 — Normalize the request

- Apply Unicode NFKC normalization and locale-independent case normalization.
- Normalize whitespace and punctuation consistently while retaining Unicode letters/numbers.
- Preserve meaningful technical symbols and terms such as `C`, `R`, `C++`, `C#`, `.NET` and `Node.js`.
- Do not drop a token solely because it has one character.
- Keep a display label separate from its comparison form and storage ID. Never derive the preferred display name from a lossy slug.

### Step 2 — Resolve the domain scope

- Use the explicit trusted domain when provided; otherwise use the existing `resolveRoadmapDomain({ domain, topic })` policy.
- Search only records whose `domainScopes` include the resolved domain, plus records explicitly designated as shared with that domain.
- Existing records without `domainScopes` are treated as belonging to their legacy `domain` only. `general` is not automatically shared.
- If the topic/domain is unknown and multiple domain candidates are plausible, return ambiguity rather than choosing the first database record.

### Step 3 — Apply deterministic identity matches

In order:

1. Exact existing canonical ID supplied from a trusted, validated registry reference, within the allowed domain scope.
2. Exact normalized preferred name.
3. Exact normalized approved alias.
4. Exact normalized slug/legacy ID, only when it identifies one record in the allowed domain scope.

A deterministic match is reusable only when exactly one compatible canonical record remains. Multiple matches are an ambiguity and must not be resolved by database ordering.

### Step 4 — Use fuzzy matching only as candidate discovery

- Generate fuzzy candidates only within the resolved domain scope.
- Score preferred names and approved aliases; retain the winning match reason and score.
- Compare the highest candidate with the second-highest candidate. A close score must be treated as ambiguous.
- Do not use the current fixed 0.8 threshold as a universal merge rule.
- Until an adjudicated benchmark establishes high-precision thresholds and a margin, fuzzy matches must be suggestions only and must not merge records or write aliases.
- After calibration, any automatic fuzzy reuse must meet the approved score, score-margin, domain and review-status gates. Store the match reason and confidence for audit.
- Candidate generation must never be treated as proof that two skills are semantically identical.

### Step 5 — Handle unmatched and ambiguous input safely

- If there is no deterministic match, create a domain-scoped provisional skill candidate or return a deterministic provisional identity to the curriculum builder, subject to an approved persistence policy.
- If multiple candidates are plausible, preserve the generated skill as provisional and record candidate references for review. Do not select a random candidate.
- Do not add generated aliases to an approved canonical record unless the input matched by exact preferred name/approved alias or an explicit reviewer approves the alias.
- A failed/ambiguous resolution must not block an otherwise valid curriculum graph; it must remain distinguishable from a confirmed canonical match.

### Step 6 — Keep registry context domain-aware

Change `getRelevantCanonicalSkills` to accept the resolved domain and return only compatible canonical records. Pass the same domain context from `generateWithGemini` into prompt construction. Sort deterministically, de-duplicate by canonical ID and return a bounded set.

The prompt must instruct Gemini to reuse supplied canonical IDs only when the generated concept is semantically the same, not merely because labels share tokens. Unknown skills should receive a new candidate identity rather than an invented existing ID.

## 5. Alias governance

- Aliases are curated identity data, not a side effect of every generation request.
- Exact normalized aliases can be reused.
- Fuzzy candidates cannot mutate aliases.
- Every alias addition should have provenance (reviewer or approved source), timestamp and normalized form.
- Alias uniqueness should be enforced within the applicable domain scope, not globally across unrelated domains.
- Alias conflicts that point to more than one concept must be marked ambiguous until adjudicated.
- Never silently rewrite an existing course's canonicalSkillId when an alias is added.

## 6. Benchmark and threshold calibration

Do not select thresholds by intuition alone. Build a versioned, adjudicated benchmark before enabling fuzzy auto-match.

Include:

- Positive pairs: exact spelling variants, punctuation/case variants, approved synonyms and common abbreviations.
- Hard negatives: related-but-distinct concepts (for example, Java vs JavaScript, React vs React Native, Data Analytics vs Data Science, SQL vs NoSQL, C vs C++, Node.js vs Node-RED).
- Same-name examples in separate domains.
- Ambiguous phrases and short labels.
- Unicode and multilingual skill names.
- Typographical errors and word-order variations.
- Existing registry records and real generated candidate examples, scrubbed of learner identifiers.

Measure at minimum:

- Precision of automatic matches (false merge rate is the critical metric).
- Recall of equivalent pairs.
- Ambiguity/abstention rate.
- Top-1 vs top-2 score margin distribution.
- Per-domain performance and performance by label length/language.
- New/provisional skill creation rate and reviewer correction rate.

Use a holdout set that is not used to tune the threshold. Prefer abstention over a false merge. The automatic-match precision target and score margin must be explicitly approved from benchmark results; this ADR intentionally does not invent a threshold.

## 7. Compatibility, migration and rollout

1. Add dedicated resolver unit tests before changing matching behavior.
2. Backfill and validate `domainScopes` from existing `domain` values without changing IDs.
3. Build the adjudicated benchmark and record baseline resolver outputs.
4. Add a shadow-resolution mode that records proposed matches/ambiguities without changing persisted canonical references.
5. Compare shadow results against the benchmark and manually inspect cross-domain collisions and false positives.
6. Enable deterministic domain-scoped matching behind a feature flag.
7. Keep fuzzy matching suggestion-only until its holdout precision and margin pass the approved gate.
8. If canonical merges are later necessary, execute a separate idempotent migration with a reference inventory and before/after audit. Do not use resolver rollout as an implicit data migration.

Do not bulk-rewrite `Course`, roadmap lesson, resource-prior, feedback or analytics IDs during the first resolver rollout.

## 8. Required tests

| Case | Expected result |
|---|---|
| Exact name in the same domain | Reuse the unique canonical ID |
| Exact approved alias in the same domain | Reuse the unique canonical ID |
| Same spelling in two incompatible domains | Return ambiguity or create a scoped candidate; never choose by row order |
| Explicitly shared skill in two domain scopes | Reuse the same canonical ID in either listed scope |
| Same slug in two domains | IDs remain distinct; no cross-domain collision |
| Near-duplicate with high top score but small top-1/top-2 margin | Abstain and return candidates |
| Related but distinct hard-negative pair | Do not merge |
| Fuzzy candidate below calibrated gate | Do not merge or mutate aliases |
| Fuzzy candidate above gate but not approved/review-eligible | Suggest only |
| New alias from an exact approved match | Add only under alias governance rules |
| One-letter technical skill (C, R) | Normalize and resolve correctly |
| Technical symbols (C++, C#, .NET, Node.js) | Preserve distinguishing tokens |
| Unicode skill label | Preserve and compare without emptying the normalized value |
| Missing/unknown domain | Use explicit fallback policy and abstain on cross-domain ambiguity |
| Database returns candidates in different order | Resolution result stays deterministic |
| Existing legacy canonical ID | Remains unchanged and resolvable |
| Relevant-skill prompt context | Contains only compatible domain records and stable IDs |

A dedicated `skillRegistry.service.test.js` suite should directly unit-test normalization, scoped candidate selection, deterministic matching, ambiguity, alias governance, provisional identities and uniqueness races. Add service-level tests verifying `buildCourse` passes the resolved domain and generated canonical IDs through the graph without losing prerequisite references.

## 9. Open decisions

1. Approve the domain-scoped, ambiguity-first identity policy.
2. Approve the representation of cross-domain skills (`domainScopes` or an equivalent explicit scope model).
3. Approve whether unmatched/ambiguous generated concepts are persisted as provisional records or remain build-local until reviewed.
4. Approve the alias-review mechanism and ownership.
5. Review benchmark results and approve the auto-match precision target, score threshold and top-1/top-2 margin.
6. Decide whether and when legacy IDs require domain-qualified migration; no ID rewrite is proposed for the initial rollout.

**Approval boundary:** This ADR documents the proposed identity policy only. It does not authorize code changes, registry migrations, alias cleanup, feature-flag changes, PR creation/merge or deployment.
